Step 7: Performance Techniques

Intro

In the previous step, the performance limitations of procedural generation were introduced. Generating terrain, biome data, and decorations can quickly become expensive, especially when this needs to happen continuously while the player is moving.

To make the system usable in practice, different techniques can be applied. These techniques do not rely on a single solution, but instead reduce the total workload from multiple angles.

1. Reducing Data and Work per Calculation

One of the simplest ways to improve performance is to reduce the amount of work that needs to be done. This can be achieved by using smaller data representations or by avoiding unnecessary calculations.

For example:

- using lower resolutions for distant terrain
- reducing the number of octaves for less important data
- skipping calculations for tiles that will not be visible or used

By limiting how much data is processed, the total number of operations can be reduced significantly.

2. Chunk-Based Generation

Instead of generating the entire world at once, the terrain can be divided into smaller sections called chunks.

Each chunk is generated independently, and only the chunks near the player are active at any given time. 

terrainChunkDictionary.Add(
    viewedChunkCoord,
    new TerrainChunk(viewedChunkCoord, chunkSize, detailLevels, transform, mapMaterial)
);

This approach ensures that the system only generates what is needed, instead of wasting time on parts of the world that are not visible.

3. Level of Detail and Distance-Based Updates

Not all parts of the world need the same level of detail. Chunks that are close to the player require high detail, while distant chunks can use simplified versions.

In the project, different levels of detail (LOD) are used, where the mesh complexity changes based on the distance to the viewer. 

if (viewerDstFromNearestEdge > detailLevels[i].visibleDistanceThreshold)
{
    lodIndex = i + 1;
}

This reduces the number of vertices and triangles that need to be processed, especially for distant terrain.

Additionally, updates are only triggered when the viewer moves a certain distance, instead of recalculating everything every frame.

4. Separating Calculation from Rendering

Another important optimization is separating data generation from Unity-specific operations. Calculations such as noise generation or biome selection do not require access to Unity objects.

This means these calculations can be handled independently, while mesh creation and object instantiation remain limited to the main thread.

By structuring the system this way, expensive calculations can be performed without blocking rendering directly.

5. Smarter Object Placement

Decoration placement can be one of the most expensive parts of procedural generation. Instead of placing objects everywhere, rules can be applied to reduce unnecessary work.

These rules include:

- sampling at intervals instead of every tile
- applying spawn chances to reduce object count
- using noise thresholds to control distribution
- enforcing minimum distances between objects

if (x % sampleInterval != 0 || y % sampleInterval != 0)
{
    continue;
}

These techniques ensure that objects are distributed in a controlled way, while also reducing the total number of checks and instantiations.

6. Incremental Processing

Instead of doing all work at once, some systems can spread their workload over multiple frames.

In the project, decoration objects are instantiated in small batches per frame. This prevents large spikes in workload and keeps the frame rate stable. 

while (nextDecorationSpawnIndex < pendingDecorationData.Length && spawnedThisFrame < decorationsPerFrame)
{
    // spawn objects gradually
}

By limiting how much work is done each frame, the system avoids sudden drops in performance.

Why These Techniques Work Together

Each of these techniques reduces performance cost in a different way. Some reduce the amount of data, others limit when work is done, and others control how detailed the result needs to be.

The important idea is that performance is not solved by a single change. It requires combining multiple strategies that together keep the system responsive.

In the next step, one specific technique will be explored in more detail: multithreading, and how it can be used to move heavy calculations away from the main thread.
