Step 7: Performance Techniques

Goal of This Step

The previous step showed that procedural world generation can become expensive when multiple systems are combined. Generating terrain data, building meshes, and placing many objects all increase the workload, especially when this has to happen continuously during gameplay.

This step mainly answers sub question 4: what techniques can be used to improve the performance of procedural generation in Unity. Instead of focusing on one single solution, this step introduces multiple optimization strategies that reduce the total cost from different angles.

Why Multiple Techniques Are Needed

There is usually no single change that solves all performance problems in procedural generation. Some optimizations reduce how much data is generated, others reduce how often work is done, and others reduce how detailed the result needs to be.

This is why performance improvements are best approached as a combination of techniques. In this project, the goal is not only to make generation faster, but also to keep the system scalable and usable in larger Unity projects.

Reducing Unnecessary Work

One of the simplest ways to improve performance is to reduce how much work the system performs in the first place. If some calculations do not significantly improve the final result, they can often be simplified, delayed, or skipped.

Examples of this include:

- using fewer octaves for less important data
- lowering resolution for distant terrain
- avoiding calculations for areas that are not currently needed

This approach was relevant for this project because the cost of procedural generation grows quickly as the world expands. Preventing unnecessary work is often more effective than trying to optimize every calculation individually.

Chunk-Based Generation

A major optimization used in this project is chunk-based generation. Instead of generating the entire world at once, the terrain is divided into smaller sections called chunks. Each chunk can be generated, displayed, and updated independently. 

terrainChunkDictionary.Add(
    viewedChunkCoord,
    new TerrainChunk(
        viewedChunkCoord,
        chunkSize,
        detailLevels,
        transform,
        mapMaterial
    )
);

This technique was chosen because it fits procedural terrain generation very well. Only the chunks near the player need to be active, while distant areas can remain unloaded. This reduces both memory usage and the amount of work the system has to do at runtime.

Level of Detail

Not every part of the world needs the same level of detail. Terrain close to the player benefits from high resolution, but distant terrain can often be simplified without the difference being very noticeable.

To handle this, the project uses levels of detail. Nearby chunks use more detailed meshes, while distant chunks use simpler versions. 

if (viewerDstFromNearestEdge > detailLevels[i].visibleDistanceThreshold)
{
    lodIndex = i + 1;
}

This reduces the number of vertices and triangles that Unity has to process. It was a logical choice for this project because the world is intended to scale across multiple chunks, making distant terrain otherwise unnecessarily expensive.

Smarter Object Placement

Another important technique is reducing the cost of decoration placement. In Step 6, object instantiation was identified as one of the main bottlenecks. Because of this, object placement needed to become more selective.

Instead of checking every position equally, additional rules can be used to lower the number of spawn attempts and the number of final objects.

These rules include:

- sampling at intervals instead of every tile
- applying spawn chances
- checking biome conditions before spawning
- enforcing minimum distance between objects 

if (x % sampleInterval != 0 || y % sampleInterval != 0)
{
    continue;
}

This was a good fit for the project because decoration is visually useful, but it should not be allowed to dominate the total generation cost. Sampling intervals and spawn rules help reduce object count while keeping the world visually varied.

Spreading Work Over Time

Even when the total amount of work cannot be fully reduced, performance can still improve by spreading that work over multiple frames. Instead of doing everything at once, the system performs part of the work incrementally.

This is especially useful for object placement. Creating many GameObjects in a single frame causes visible lag spikes, while spawning them gradually reduces those spikes. 

while (nextDecorationSpawnIndex < pendingDecorationData.Length &&
       spawnedThisFrame < decorationsPerFrame)
{
    // spawn objects gradually
}

This technique was particularly relevant in this project because the largest observed problem was not only the total cost, but the sudden peak in cost when many objects were instantiated at once.

Separating Data Generation from Unity-Specific Work

Another useful optimization strategy is separating calculation from application. Many parts of procedural generation only operate on data, such as generating noise values, determining biome types, or preparing spawn positions. These steps do not necessarily require direct interaction with Unity objects.

By separating this data processing from rendering and object creation, the system becomes easier to optimize. This idea also prepares the project for multithreading, which is explored in the next step.

Why These Techniques Fit This Project

These optimizations were not chosen randomly. They fit the structure of this project because the generator is intended to become a reusable Unity tool, potentially even as an Asset Store package. That means the system should not only work in one small demo scene, but remain practical in larger and more demanding environments.

Chunking helps scale the terrain, level of detail reduces rendering cost, smarter spawning reduces decoration overhead, and incremental processing prevents major lag spikes. Together, these techniques make the system much more suitable for real-time use.

What This Step Adds to the System

This step expands the project from identifying performance problems to actively addressing them. It shows that procedural generation does not become usable in practice through one optimization, but through a collection of strategies that reduce different kinds of workload.

This directly contributes to sub question 4 by showing several practical techniques for improving performance in Unity. In the next step, one of the most important of these techniques is discussed in more detail: multithreading.
