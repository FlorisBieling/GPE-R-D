Step 8: Multithreading

In the previous step, multiple techniques were introduced to reduce the workload of procedural generation. One of the most powerful techniques is multithreading, which allows heavy calculations to run separately from the main Unity thread.

To understand why this matters, it is important to first understand how Unity handles execution.

Main Thread vs Worker Threads

Unity uses a main thread to handle almost everything: rendering, updating objects, physics, and most engine-related operations. This means that if too much work is done on the main thread, the frame rate will drop.

Multithreading introduces additional threads, often called worker threads. These threads can perform calculations independently from the main thread.

In this project, this separation is used to move expensive calculations away from rendering.

What Can and Cannot Run on Threads

Not all code can safely run on a separate thread.

Calculations that only work with data can be moved to worker threads. This includes:

- noise generation
- biome calculations
- decoration spawn data generation
- mesh data generation (vertices, triangles, UVs)

However, Unity objects cannot be accessed from worker threads. This means the following must stay on the main thread:

- creating GameObjects
- modifying transforms
- assigning meshes or materials

Because of this, the system must split work into two parts: calculation and application.

How Multithreading Is Used in This Project

In this project, map generation is performed on a worker thread. Instead of directly generating data on the main thread, a request is created and processed in the background. 

public void RequestMapData(Vector2 centre, Action callback)
{
    ThreadStart threadStart = delegate
    {
        MapDataThread(centre, callback);
    };

    new Thread(threadStart).Start();
}

The worker thread generates the data and stores the result in a queue. 

void MapDataThread(Vector2 centre, Action callback)
{
    MapData mapData = GenerateMapData(centre);

    lock (mapDataThreadInfoQueue)
    {
        mapDataThreadInfoQueue.Enqueue(new MapThreadInfo<MapData>(callback, mapData));
    }
}

This ensures that the heavy calculations do not block the main thread.

Returning Data to the Main Thread

Because Unity objects can only be modified on the main thread, the generated data must be returned safely.

This is done using a queue that is processed during the Update loop. 

void Update()
{
    lock (mapDataThreadInfoQueue)
    {
        while (mapDataThreadInfoQueue.Count > 0)
        {
            MapThreadInfo<MapData> threadInfo = mapDataThreadInfoQueue.Dequeue();
            threadInfo.callback(threadInfo.parameter);
        }
    }
}

The callback is then executed on the main thread, where it is safe to create meshes, textures, and objects.

Applying the Result in Unity

Once the data is returned, it can be used to build the world. For example, meshes can be generated and assigned, and textures can be applied to represent the biome result.

This step is where the system transitions from background computation back to visible results in the scene.

The Full Flow

The complete process can be summarized as follows:

1. Request generation of map data
2. Perform calculations on a worker thread
3. Store results in a thread-safe queue
4. Retrieve results on the main thread
5. Apply results to Unity objects

This structure allows the system to handle heavy calculations without interrupting rendering or gameplay.

Why This Is Important

Without multithreading, generating terrain, meshes, and decorations would all happen on the main thread. This would quickly lead to frame drops or freezing, especially when generating multiple chunks.

By moving the expensive parts of the system to worker threads, the main thread remains responsive, making real-time procedural generation possible.
