Step 8: Multithreading

Goal of This Step

The previous step introduced several techniques for improving the performance of procedural generation in Unity. One of the most important of these is multithreading. This step continues answering sub question 4 by explaining how multithreading can be used to reduce frame drops and make real-time generation more practical.

Why Multithreading Was Relevant in This Project

In this project, one of the clearest performance problems was the sudden lag that occurred when large amounts of generation work happened at once. A major example of this was decoration spawning. When too much work was performed in a single frame, Unity stalled visibly.

Because of this, it became necessary to move as much heavy calculation as possible away from the main thread. Multithreading was a suitable choice because much of procedural generation is based on data processing rather than direct interaction with Unity scene objects.

Main Thread and Worker Threads

Unity uses a main thread for most engine-related tasks, including rendering, physics, and object creation. If too much work is done on this thread, the frame rate drops and the game can start to stutter.

Multithreading introduces additional worker threads that can perform calculations separately from the main thread. This makes it possible to prepare data in the background while the main thread remains focused on running the game.

What Can and Cannot Run on a Thread

Not every part of a Unity project can safely run on a worker thread. The main rule is that calculations based only on data can usually be moved to another thread, while anything that directly uses Unity objects must stay on the main thread.

In this project, the following kinds of work are suitable for worker threads:

- generating noise maps
- calculating biome data
- preparing mesh data such as vertices and triangles
- preparing decoration spawn data

The following kinds of work must remain on the main thread:

- creating or destroying GameObjects
- modifying transforms
- assigning meshes, textures, or materials
- interacting directly with Unity components

This distinction is important because multithreading is not a universal solution. It can reduce the cost of calculation, but Unity-specific work still has to be applied safely on the main thread.

How Multithreading Is Used in the Project

In the project, map generation is requested from the main thread, but the actual calculation is performed on a worker thread. This means the heavy data generation does not immediately block the frame. 

public void RequestMapData(Vector2 centre, Action callback)
{
    ThreadStart threadStart = delegate
    {
        MapDataThread(centre, callback);
    };

    new Thread(threadStart).Start();
}

This method creates a new thread and starts the background generation process. The data itself is then calculated separately from the main Unity loop. 

void MapDataThread(Vector2 centre, Action callback)
{
    MapData mapData = GenerateMapData(centre);

    lock (mapDataThreadInfoQueue)
    {
        mapDataThreadInfoQueue.Enqueue(
            new MapThreadInfo<MapData>(callback, mapData)
        );
    }
}

Why a Queue Is Needed

Once the worker thread finishes its calculation, the result cannot simply be applied directly to the scene. Unity objects must still be updated on the main thread. Because of this, the generated data is placed into a queue.

The queue acts as a safe handoff between the worker thread and the main thread. The background thread calculates the result, and the main thread later retrieves it and applies it when it is safe to do so. 

void Update()
{
    lock (mapDataThreadInfoQueue)
    {
        while (mapDataThreadInfoQueue.Count > 0)
        {
            MapThreadInfo<MapData> threadInfo =
                mapDataThreadInfoQueue.Dequeue();

            threadInfo.callback(threadInfo.parameter);
        }
    }
}

This structure keeps the expensive calculation separate from the Unity engine operations, while still making it possible to use the generated data in the scene.

Why This Was a Good Choice for the Project

Multithreading was a strong fit for this project because the system is built around repeated map and biome calculations. These calculations are relatively heavy, but they do not need immediate access to scene objects while they are being generated.

That makes them suitable to move into the background. Instead of freezing the game while chunks are prepared, the system can calculate data separately and only apply the result when ready.

This is especially valuable for a reusable terrain generation tool. If the system is intended to be used in larger Unity projects or even distributed as an Asset Store package, it needs to remain responsive while generating terrain in real time.

Limitations of Multithreading

Even though multithreading is powerful, it does not solve every performance problem by itself. If too many objects still need to be instantiated on the main thread, lag can still occur. In other words, threading reduces the cost of preparing data, but it does not remove the cost of applying that data in Unity.

Because of this, multithreading works best when combined with the techniques from the previous step, such as chunking, level of detail, selective spawning, and spreading work over time.

What This Step Adds to the System

This step completes the performance section of the project by showing how one of the most effective optimization techniques can be applied in Unity. It demonstrates that procedural generation can be made more practical by separating heavy calculations from engine-side object updates.

This directly contributes to sub question 4, because it explains how multithreading improves performance and why it was a suitable choice for this project.
