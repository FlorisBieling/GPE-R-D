Step 6: Performance Problems

Goal of This Step

In the previous step, the procedural system was extended into a complete Unity pipeline, where noise data was used to generate terrain meshes, textures, and object placement. While this makes the system much more useful, it also introduces a new challenge: performance.

This step mainly answers sub question 3: what performance challenges occur when generating large procedural worlds in real time.

Why Performance Becomes a Problem

Procedural generation requires a large number of calculations. Even a single map involves iterating over every position in a grid and sampling multiple layers of noise. When this is expanded to a full system with chunks, meshes, and object placement, the amount of work increases rapidly.

What worked well for small demos in earlier steps becomes much heavier when applied continuously during gameplay. Instead of generating one map, the system now generates multiple chunks, each with their own data and objects.

Where the Cost Comes From

The main performance cost comes from several combined factors:

- nested loops for noise generation
- multiple data layers (height and temperature)
- mesh generation for each chunk
- biome checks for every tile
- object placement logic and instantiation

These systems all build on top of each other. While each individual step may be manageable, together they significantly increase the total workload.

Nested Calculations and Scaling

One of the main reasons performance becomes an issue is the use of nested loops. For every position in the map, multiple noise calculations are performed. When using multiple octaves, each position already requires several function calls.

When the map size increases, the total number of operations grows very quickly. A relatively small map can already require tens of thousands of calculations, and this cost multiplies when multiple chunks are generated.

Object Placement as a Bottleneck

A major issue observed in this project was object placement. When many objects, such as trees or grass, were instantiated at once, Unity tried to process all of them in a single frame.

This caused noticeable lag spikes. The frame would freeze temporarily while all objects were created, which made the system unsuitable for real-time use.

This shows that object instantiation can be more expensive than the underlying noise calculations. Even if the data generation is efficient, creating large numbers of GameObjects at once can become a major bottleneck.

The Unity Main Thread

Another important limitation comes from how Unity handles execution. Most operations, including rendering, physics, and object creation, run on the main thread. This means that if too much work is done at once, the entire frame is delayed.

Because of this, even if individual calculations are relatively simple, performing too many of them in a single frame can lead to stuttering or freezing.

Why Real-Time Generation Is Different

In earlier steps, maps were generated as isolated demos. In those cases, performance was less important because the generation only happened once.

In a real-time system, this is very different. New terrain chunks must be generated continuously as the player moves through the world. This means the system must balance generation speed with frame stability.

What was acceptable in a static preview becomes a problem when the same work needs to be repeated during gameplay.

Why These Problems Matter

These performance issues highlight an important limitation of procedural generation. While it is powerful, it is not free. As the system becomes more complex, the cost increases quickly.

Without optimization, the system can suffer from frame drops, lag spikes, or unresponsive behavior. This makes it unsuitable for real-time applications such as games.

This directly answers sub question 3: generating large procedural worlds in real time introduces significant computational cost, especially when combining multiple systems such as noise generation, mesh creation, and object placement.

What This Step Adds to the System

This step does not introduce a new feature, but instead analyses the limitations of the current system. It identifies where the main bottlenecks occur and why the current approach is not yet efficient enough.

Understanding these problems is essential before applying optimizations. In the next step, different techniques will be explored to reduce the workload and improve performance.
