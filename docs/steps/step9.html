Step 9: Endless terrain, LOD, threading and refactoring

Runtime architecture

The final step is not another visual feature. It is the structure that allows all earlier systems to run while the player moves through an endless world.

Chunk streaming

EndlessTerrain converts the viewer position into chunk coordinates. Existing chunks are updated, missing chunks are created, and chunks outside the maximum view distance are hidden. The expensive visibility scan only runs after the viewer has moved beyond a configured threshold.

Level of detail

Each visible chunk chooses a mesh LOD from its distance to the viewer. Near chunks use a dense mesh and are allowed to show decorations. Distant chunks use larger vertex steps and keep decorations disabled. 

int meshSimplificationIncrement = levelOfDetail == 0
    ? 1
    : levelOfDetail * 2;

int verticesPerLine = (width - 1) / meshSimplificationIncrement + 1;

Background calculation and main-thread handoff

Map data, mesh data and decoration data are calculated on worker threads. The result is placed in a locked queue. MapGenerator.Update drains those queues and invokes callbacks on Unity's main thread, where textures, meshes and GameObjects can be safely created or assigned.

Why MapGenerator was split

The old class combined configuration, biome rules, control maps, snow, decorations, preview logic and threading. The current version keeps MapGenerator as the coordinator and moves specialised calculations into focused classes.

MapGenerator.cs

Settings, map requests, editor preview and thread-result queues.

BiomeGenerator.cs

Biome selection, fallback logic and preview-color smoothing.

BiomeControlMapGenerator.cs

Texture weights, boundary noise, patch noise and snow masking.

DecorationGenerator.cs

Deterministic spawn-data generation and minimum-distance checks.

TerrainData.cs

Shared data structures and the biome texture enum.

EndlessTerrain.cs

Chunk lifetime, LOD selection, material assignment and gradual spawning.

Why this folder structure was chosen

Compared with one flat Assets folder

Files are grouped by responsibility

Materials, editor tools, generation code, runtime code and shared data can be located without searching through unrelated assets.

Unity-specific choice

Editor-only code has a clear build boundary

The texture-assignment utility belongs in Editor because it uses UnityEditor and AssetDatabase, while runtime builds only need the resulting material.

Maintenance choice

Filenames match their MonoBehaviour classes

TopDownCameraMovement.cs and CameraHeightControl.cs are easier to find and attach than generic or mismatched filenames.

When the project grows further

Assembly definitions could make boundaries even stronger

The current folder structure is sufficient for this project. Separate assemblies become useful later when compile times, package reuse or stricter dependencies matter.

Camera helper scripts

TopDownCameraMovement reads the legacy Horizontal and Vertical axes, moves along the camera's flattened forward/right directions, and multiplies speed while Left Shift is held. CameraHeightControl moves the viewer vertically with M and N and clamps the height between 5 and 800 Unity units.

Compared with a complete player controller

Fast free-camera inspection

The small helper scripts are enough to cross chunk borders, inspect LOD changes and change viewing height without adding unrelated gameplay systems.

Chosen for the research scene

Simple controls keep testing reproducible

Fixed movement axes and height keys make it quick to repeat the same terrain checks during development.

Optional package upgrade

Expose bindings through the Input System

A reusable public package could make the controls configurable. For the current research scene, the smaller legacy-input solution is appropriate.

Why the runtime architecture is a good fit

Chunk streaming

Work follows the viewer instead of the theoretical world size

Only nearby chunks need active meshes and materials, which makes an apparently endless world practical.

Level of detail

Mesh complexity is spent where it is visible

Near chunks retain detail while distant chunks use larger vertex steps, reducing geometry cost without changing the underlying world data.

Thread handoff

Data work is separated from Unity object work

Worker threads prepare maps and mesh data, while locked queues return results to the main thread where Unity APIs are safe to use.

Next scalability step

Use a bounded job scheduler when request volume grows

Raw threads are easy to understand and suitable for the current project. Unity Jobs, Tasks or a thread pool would become preferable if many chunks request work simultaneously.
